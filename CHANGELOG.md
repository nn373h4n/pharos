# Changelog

All notable changes are listed here, newest first. The format follows [Keep a Changelog](https://keepachangelog.com/) and the project uses [Semantic Versioning](https://semver.org/).

## [Unreleased]

### Added

- `python -m pharos.cli list-people` (read-only, as the application role): the organization's people with the identifier that `delete-person --user-id` takes, how they sign in, role, status, last sign-in, name and e-mail, 100 at a time; characters that could drive the terminal are escaped (F-57).
- Signing in with an account whose password hash was made with older, cheaper parameters (or whose hash is damaged) takes as long as signing in with an unknown name, alone or among parallel requests (F-16).
- Passwords in the database and Redis addresses may contain only letters, digits and `_ . -`; anything else is refused at start-up by the services, the migrations, the operator commands and, on a new volume, PostgreSQL's init script, instead of being read as another password or another host (F-09).
- `/api/readyz` runs its checks at most once every 2 seconds; calls in between get the last report, and calls during a round wait for it (F-10).
- The Model page shows how many more insights today's budget covers, at the average cost of the last seven days' insights or, before the first one, at the worst case at the set prices (F-52); `GET /api/llm/status` has `insights_left`. The pilot runbook sizes the budget with the numbers ("How many insights a day"): the default of two dollars a day covers at most a handful of insights at the default prices.
- `scripts/restore.sh` compares the restored database with what the migrations make at the dump's own schema version (owners, grants, row-level security and policies, functions and their rights, triggers and other objects, the database's grants) and stops on any difference, naming it; it reads with names resolved in `pg_catalog` only and refuses extensions Pharos does not make, compares table persistence (an `UNLOGGED` audit log), the database's own flags and comments, and refuses a restore that changed any role, membership or role setting (F-44). After a failed restore it says to remove the postgres volume: a hostile dump can keep part of what it wrote. `scripts/backup.sh` refuses a directory with a POSIX access control list and one under a parent that others can write to; `scripts/restore.sh` asks the same of the directory of its private copy.
- `make test-compose` restores a real dump cut short (refused at the listing when cut in half; stopped partway, with the advice to remove the volume, when only its last bytes are missing). The docs no longer say that the restored "audit chain and tokens" cannot be read without the root secret: nothing in the database is encrypted with it; it keys the audit log's address hashes (F-45).
- A source's host is compared the way the HTTP client connects to it (IDNA 2008): `straße` and `strasse` are no longer one source, and a host with invisible or full-width characters is refused (F-22).
- Caddy no longer runs as root: it runs as uid 65532 with no capability and binds 80 and 443 through a sysctl of its own network namespace. A one-shot `caddy-volumes` service hands its volumes to that user on every start, so an upgraded installation needs no manual step (F-08, ADR-0010 amendment).
- The development Keycloak's administrator password is `PHAROS_KEYCLOAK_ADMIN_PASSWORD`, random per installation (`make env` makes one; add it to an older development `.env`), not a fixed password from this repository; `PHAROS_BIND_ADDRESS` publishes the ports on one address only, and the SSO check and the load test use 127.0.0.1 (F-54).
- `scripts/status.sh` shows how long ago the worker's heartbeat was written (WARN after 90 seconds; readyz fails only after 210) and the newest dump's size (FAIL when empty, WARN when less than half the one before); `make test-compose` now runs it on the real stack (F-59).
- `make check-catalogue` (`scripts/starter-catalogue-check.sh`): every starter source fetched once from the real internet on a throwaway stack, manual and never in CI (M5-08). First run: 25 of 25 sources ok.
- The pilot runbook has "Rotating a secret": a table per secret and a procedure that changes the database passwords inside PostgreSQL (editing `deploy/.env` alone left the old password valid), and crontab lines for the backup and retention jobs. `scripts/status.sh` also fails for a stopped service outside the default profile (the local model), for any stopped container of a service, and for a dump dated even minutes in the future (second review of M5-11).

## [0.1.0] - 2026-11-10

First release. Upgrade notes: none, there is no earlier release to upgrade from. (Two entries under Changed below describe steps for installs made during development; a new install via `make env` needs neither.)

### Not ready in this release

Said plainly so nobody reads a missing item as done:

- Egress control for the containers (M5-03, F-04, F-06), the worker boundary checks (M5-05) and the model-layer leftovers (M5-06) wait for gate G1: the ADRs they amend (0022 to 0025 and the older Proposed ones) are still `Proposed`.
- The pilot runbook and production checklist (M5-11) exist, but were rehearsed only on images built from `main`, not on this release's published images; its egress line says plainly that there is nothing to tick. The whole-milestone security review and readiness report (M5-13) are not done.
- The release chain itself (`publish`, `sign`, keyless signing on GitHub, anonymous verification) has not run yet; this tag is its first run.

### Fixed

- A feed in an encoding the XML parser does not know (for example EBCDIC) could hide its document type declaration from the check that refuses declarations and entities; such a feed is now refused (found by the whole-milestone review of M3).
- Caddy listens on the same port numbers the host publishes, and the HTTP-to-HTTPS redirect now names the configured domain and HTTPS port. The automatic redirect reflected the request's Host header, an open redirect; it is disabled and `make test-compose` checks it.

### Changed

- Base images, `uv` and `pnpm` are pinned by digest or hash in the Dockerfiles and Compose files (M5-10a, F-05); Dependabot opens the bump PRs, and a reviewer must check each digest bump.
- An insight asked for past the minute's limit of calls to the model is no longer dropped (F-51): the worker tries again at the start of the next minute, at most four times. Before, the person waited five minutes and asked again; in a burst of 100 people at once all 100 now get their insight in under three minutes (p95 157 s), no server errors.
- The Home feed no longer ranks every article of its window on every request (F-49, ADR-0027, `Proposed`): the shared part of the ranking of each profession is made once in five minutes and kept in Redis; each request adds the person's own part. On the load test (30,000 articles, a 2-thread machine) the first page went from p95 6.3 s to 134 ms with 50 people at work and the stack no longer fails with 300. New or changed rankings show up to five minutes late; a held or hidden article disappears at once.
- Redis now has two users instead of one shared password (follow-up F-14): `pharos_api` for the API and `pharos_worker` for the worker and the scheduler. The worker's user can use only the Celery queue and `pharos:worker:*`, so a compromised worker can no longer forge or read sessions. **Upgrading:** add `PHAROS_REDIS_WORKER_PASSWORD` (a new random value, different from `PHAROS_REDIS_PASSWORD`) to `deploy/.env` before `docker compose up`; `make env` generates it for new installs.

- The worker and the scheduler connect to PostgreSQL as their own role, `pharos_worker`, which has no privilege on people, credentials, profiles or the audit log, and the worker refuses to start with any other role. Tasks have time limits, worker processes are recycled, and the scheduler (`beat`) no longer has a route to the internet. **Upgrading:** add `PHAROS_WORKER_DB_PASSWORD` to `deploy/.env` and recreate the database volume (the role is only created on first start); see `docs/DEPLOYMENT.md`, "Upgrading to M3".

- Docker logs rotate by size: each container's log is capped by `PHAROS_LOG_MAX_SIZE` (default `10m`) and `PHAROS_LOG_MAX_FILE` (default `5`) instead of growing without limit. Both settings are in `deploy/.env.example`.

### Added

- Pilot runbook, production checklist and participant briefing template (M5-11): `docs/guides/pilot-runbook.md` (install, first sign-in, sources, model key and budget, approved tools, daily checks, backups and retention, incidents, upgrade and rollback, end of the pilot) and `docs/guides/pilot-briefing-template.md` (what to tell people about pasting data into AI tools, what is stored, what reaches a model). `make status` (`scripts/status.sh`) is a read-only look at a running installation: services, readiness, the age of the newest backup, the disk.
- Release workflow, first part (M5-10b): on a tag `vX.Y.Z` on main, the workflow builds both images, scans them with Trivy, makes an SBOM per image and pushes them to GHCR; a pull request that changes the workflow runs the build and scan as a dry run. No GitHub Release is cut.

Not yet run on GitHub: no tag exists.
- Release preparation (M5-10d): a tag must equal the version in the code before anything is built; `deploy/docker-compose.release.yml` runs the published images by digest; `scripts/verify-release.sh --backend <ref> --web <ref>` checks your digests against the release's; the steps, the release notes template and the install and rollback notes are in `docs/guides/releasing.md` and `docs/DEPLOYMENT.md`.
- Tests and a written rule for F-47 (M5-09 follow-up, no behaviour change): the monthly interaction counts are not shown to anyone who could see the daily summary while those months were recent (administrators), nor together with overlapping periods; tests guard against a future change in the repo or the database; see ADR-0025 and `docs/DEPLOYMENT.md`.
- `LOAD_SCENARIO=insights make loadtest` (M5-08): the insight burst, with the stack's test provider; see `docs/DEPLOYMENT.md`.
- `LOAD_SCENARIO=sso make loadtest` (M5-08): 100 synthetic people sign in through a development Keycloak from one address; all 100 signed in, no 429, 5xx or timeout, one sign-in p95 264 ms, the last one in at 99 s; see `docs/DEPLOYMENT.md`.
- `make test-resilience` (M5-08): a 10,000-entry feed is read within the worker's memory (peak 215 MiB, limit 300), and a worker killed with `docker kill` in the middle of a fetch loses and doubles nothing after its lease runs out; see `docs/DEPLOYMENT.md`, "Resilience check".
- `make loadtest` (M5-08, first part): the Home feed under load on a throwaway stack with synthetic data (k6 pinned by digest; report with the hardware and a verdict on each D5 target). It showed that the cost of a feed request grew with the number of articles (F-49, fixed in Changed); with the fix the D5 feed target is met on a 2-thread development machine. See `docs/DEPLOYMENT.md`, "Load test".
- Network and HTTP leftovers (M5-04, closes F-17, F-20 and the body-size part of F-25): the identity provider's signing keys are read again after an hour and every call to the provider has one overall deadline (15 s, 6 s for Graph); `SafeHttpClient` also refuses the addresses that `PHAROS_PUBLIC_URL` resolves to (any name, any spelling, looked up again every minute), looks names up with a time limit on a small pool of its own, and `Settings` cannot be changed after start-up; Caddy sends `Strict-Transport-Security` (`PHAROS_HSTS_MAX_AGE`, default one year) and, like the API (`413 payload_too_large`), refuses request bodies over 1 MiB.
- Retention and deleting one person's data (M5-09, ADR-0025, stays Proposed; see `docs/DEPLOYMENT.md`, "Retention and deleting a person"): the audit log and interactions are kept for `PHAROS_AUDIT_RETENTION_DAYS` (default 365, lowest allowed 30) and `PHAROS_INTERACTIONS_RETENTION_MONTHS` (default 12, lowest allowed 3). Three operator commands do the work: `delete-person` removes one person's profile, interactions, feeds and sessions and leaves one audit entry without content; `prune-audit` deletes audit rows past their retention, as the database owner; `fold-interactions` turns old interactions into monthly counts. A new Compose profile `operator` runs one such command with a narrow set of environment variables and exits; it is not started by `up`. Migration 0011 adds `interaction_counts_monthly`, which publishes a count only for at least five people. Nothing runs the two prune commands on a schedule yet (F-48), and the monthly counts next to the daily summary may reveal a smaller group by subtraction (F-47).
- Approved AI tools and "Open in" (M5-07, ADR-0026, closes F-35): administrators keep a list of up to ten AI tools, each with a name and an https address, on the `/ai-tools` page; everybody signed in can see the list. "Try this" shows a plain "Open in" link with the tool's host beside it; it opens in a new tab and carries nothing from the card, so the person copies the prompt first. The list is empty by default, and the card offers Copy only until tools are added; which tools to approve is the operator's decision (gate G9). Changes are audited by identifier only. Migration 0010 adds `ai_tools`. Four languages; the az, tr and ru wording is unreviewed (F-01).
- Backup and restore, rehearsed (M5-02, ADR-0022; see `docs/DEPLOYMENT.md`, "Backup and restore"): `scripts/backup.sh` writes a custom-format PostgreSQL dump as the database owner through the container's local socket (no password on a command line), reads it back to its end and writes a SHA-256 file beside it; it keeps 7 daily, 4 weekly and 3 monthly dumps and runs one at a time. `scripts/restore.sh` checks the checksum, refuses a database that is not new and empty, and restores in one transaction into a database whose roles already exist. `make test-compose` backs up the stack, destroys its volumes, restores into a new database and checks that the schema, row counts, row-level security, policies, grants, functions and roles match before and after, that the Home feed shows the same article, and that a session from before the backup no longer works (Redis is not backed up, so people sign in again). **The dump is code:** restoring a dump from an unknown source is a trust decision. The after-restore check looks only at database and role settings and extra schemas, so a hostile dump can pass (F-44); restore only a dump whose origin you trust. Not rehearsed: a restore on the pilot server, a large database, an older dump restored into a newer version, a real truncated dump, and the audit chain after a restore. Nothing alerts on a missed backup (F-45); the off-host copy and encryption are the operator's.
- Near-duplicate articles (M4-05, ADR-0007 amendment, ADR-0021): with `PHAROS_EMBEDDING_PROVIDER` set, a worker sweep embeds the public articles the model has read (migration 0009: `item_embeddings`, `items.cluster_id`, the stage `embedding` in the usage record), joins an article to the cluster of its nearest recent neighbour above `PHAROS_EMBEDDING_SIMILARITY`, and the Home feed shows one card for a story, the copy seen first. Nothing is merged or deleted. The model and the threshold are the operator's choice; `python -m pharos.evaluation dedup` tunes the threshold on labelled pairs. Measured on a synthetic corpus of syndicated copies with the demo embedder: 1 duplicate in 61 cards (1.6%), no story lost. Nothing is claimed for any real model or language; the default threshold (0.92) did not separate same-story pairs with one model tried (bge-m3) (F-36, F-42).
- The local model (M4-10, ADR-0020): `PHAROS_LLM_PROVIDER=ollama` calls a model server that runs in Compose (profile `local-llm`) on an internal network with no route to the internet; it takes no key and no address; a separate one-shot job (`scripts/ollama-pull.sh`) downloads models; the model page names it. No claim of "fully local" or of quality is made (F-36).
- Limits on suggestions (M4-11, from the whole-milestone review): one person may ask for at most 30 "Try this" suggestions a day (besides 120 an hour), and suggestions may use only half of the day's model budget, so people asking for them cannot stop the reading of new articles for everyone; the reserve step enforces the ceiling atomically and does not mark the day as exhausted.
- Real-stack tests of the model layer (M4-11): with the worker alone running the test provider, the stack tests prove that an article is fetched, read by the filter and the enrichment, shown as a card for the profession it fits, that "Try this" is made by the worker and shown, that a save is stored, that the model page shows the spending and never a key, that at 80% of the day's limit an administrator is warned and at 100% no new article is read while the existing cards and insights keep showing, and that the model calls are booked as numbers only. The `fake` provider (`PHAROS_LLM_PROVIDER=fake`, refused in production) now answers every task with a valid, deterministic answer instead of an empty object, so it can serve demos.
- The evaluation of the model output in Azerbaijani, Turkish, Russian and English (M4-09): `python -m pharos.evaluation` exports a corpus from the installation's own public articles, runs candidate models through the product's gateway and prompts, writes blind rating sheets for native speakers, imports their marks strictly, and reports which model clears the bar (and the lines for `.env`). No automated judge counts. Guide in `docs/guides/evaluation.md`. The first real run needs raters and a key and is still to be done.
- The Home screen (M4-08): the ranked cards with Save, Useful, Not useful (with undo), and **Try this**: how the article applies to your profession, a prompt to copy with a data note, and buttons to report that you tried it and the minutes it saved; in all four languages. A strict Content-Security-Policy with a nonce per request is now set on every page (ADR-0019, closes F-03). The approved-tools list is a later step.
- The Home feed and interactions (M4-07, ADR-0018): `GET /api/cards` ranks the public articles the model has read by the profession's fit, recency, quality and a nudge from the person's interests and level, with stable paging; `PUT/DELETE /api/items/{id}/interactions/{kind}` records save, useful, not useful, tried and minutes saved, private to each person by a database policy; `GET /api/interactions/summary` gives administrators counts only, hiding any figure on fewer than five people. Migration 0008.
- Insights (M4-06): `GET /api/items/{id}/insight` gives, for the asking person's profession and language, how an article applies and one prompt to try, made by the worker when a card is first viewed and cached per (article, profession, language, prompt version). The prompt must pass a strict validator (placeholders, no data, no secret words in four languages, no hidden characters) before it is stored and again before it is served. Migration 0007 adds `item_insights`. The insight prompt is now version v2.
- The article card shows the model's summary and category as plain text, and reviewers also see its quality score and the hold reason `low_quality` (M4-04b); in all four languages.
- Enrichment of public articles by the model (M4-04a, ADR-0017): a summary, a category, a quality score and the fit to each profession, read every minute in small batches within the day's limit. Poor, off-topic or suspicious articles are held for an editor as `low_quality`. Migration 0006 adds the columns, `item_professions`, the SAP Basis administrator profession and the narrow right of the worker to hold a new article (nothing else about an article's state).
- The model page for administrators (M4-03, `/llm`): provider, models, today's spending with a warning at 80% and a notice when the limit is reached, the last key check with a "Test the key" button, and seven days of usage; in all four languages. Wording of az, tr and ru is not yet reviewed by a native speaker (F-01).
- Administrator API for the model layer (M4-03): provider, models, daily cap and spending, seven-day usage, and "test the key", a worker task that makes one tiny audited and budgeted call. The provider's address is looked up and must be public before the first call. The key stays in the worker's `.env`. A configured provider address gets a client that follows no redirect, so a redirect cannot carry the key to a host nobody looked up.
- The model gateway (milestone M4, `pharos.llm`): the one door to a language model, on the LiteLLM SDK (pinned). Only public article text can be sent, text is masked, the model has no tools, answers must fit a schema, spending is booked before each call against a small daily cap (80% warning, 100% stop, fail closed), and nothing about the content is logged. Off by default (`PHAROS_LLM_PROVIDER=off`); a fake provider serves tests and demos. Migration 0005 adds the content-free usage record `llm_usage`.
- Real-stack tests for ingestion (milestone M3, `make test-stack-e2e`): a fake feed host that only the worker can reach (a test-only Compose overlay), the whole path of an article, hostile and huge feeds, the places inside the stack that the worker must never reach, personal feeds and a disabled owner, and accessibility of the new pages.
- The feeds of a person whose account is disabled or deprovisioned are no longer fetched (follow-up F-32, migration 0004): the worker role may read the state of an account (`users.org_id`, `id`, `status`) and nothing else about people, takes only the personal feeds of active owners when it leases, and checks again before it fetches. ADR-0014 (proposed).
- Personal feeds (milestone M3, `pharos.feeds` and the page `/my-feeds`): every signed-in person can follow up to five RSS or Atom feeds of their own, fetched at most hourly, with their latest fetches and articles, seen by nobody else (not an administrator, not another organization). The address is checked like an organization source and a refused address is audited; `PHAROS_PERSONAL_FEEDS=off` removes the feature. No database migration.
- `python -m pharos.cli import-sources [--file PATH] [--dry-run]` (milestone M3): adds the starter catalogue of public sources to the organization, every source switched off, all or nothing, never changing a source that already exists. The catalogue file is checked with the rules of the Sources API; the list that ships has 25 public sources approved by the maintainer (16 feeds, 7 GitHub repositories, 2 Hacker News searches), each checked against Pharos's own feed rules before it was listed.
- Scheduled fetching (milestone M3, `pharos.ingest`): every minute the worker leases the sources that are due and fetches each one, at most 20 per minute, one request per host every five seconds, with no database transaction open while it waits for the network. Failures back off (doubling up to a day, `Retry-After` obeyed); a source that keeps failing is tried once a day. Old fetch history, raw items and items are removed on a schedule. Fetched entries are stored as raw items; turning them into items is the next step (M3-08).
- The RSS and Atom connector and the feed parser (milestone M3, `pharos.ingest`): a feed is refused if it has a document type declaration, an entity or an external reference, or is absurdly large or deep; titles and excerpts become short plain text without markup, look-alike or invisible characters; only absolute `http(s)` links are kept; fetches are conditional (`ETag`, `Last-Modified`) and go through `SafeHttpClient`. New dependencies: `feedparser`, `nh3`, `defusedxml`. Nothing schedules it yet (M3-07).
- Database tables for sources and ingestion (migration 0003, milestone M3): `sources`, `fetch_runs`, `raw_items`, `items`, `item_sources`. They belong to the organization under row-level security; a personal feed is visible to its owner only, administrators included; the worker role gets column-level access to these tables and nothing else. Run `docker compose ... run --rm migrate` after upgrading (the demo default applies it on start).
- `SafeHttpClient` (milestone M3): the only way connectors reach the internet. It checks every address a name resolves to at connect time and connects to the checked address (no DNS rebinding window), follows at most 3 redirects and re-checks each hop, allows only ports 80 and 443, refuses credentials in URLs and compressed answers, caps the body at 2 MiB and the whole request at a wall-clock deadline, ignores proxy environment variables, and returns only coarse error kinds. A bearer token is sent only over HTTPS to its own host. Import-linter now limits `httpx` and `httpcore` to this client and the identity-provider client, and keeps API modules from importing the fetcher.
- Platform skeleton (milestone M1):
  - Backend: FastAPI application with request ids, JSON logs that mask secrets, `/api/healthz` and `/api/readyz`, and an Alembic baseline that creates `organizations` under PostgreSQL row-level security.
  - Worker: Celery worker and scheduler with a heartbeat that `/api/readyz` checks.
  - Web app: Next.js pages in English, Azerbaijani, Turkish and Russian, light and dark themes, WCAG 2.2 AA checks in the test suite.
  - Deployment: Docker Compose stack with Caddy, isolated networks, hardened containers, PostgreSQL with pgvector and Redis (`make env`, `make dev`).
  - Delivery: pull-request checks, security scans (gitleaks, CodeQL, Trivy), weekly Dependabot updates, a protected `main` branch.
- Development identity provider: `deploy/docker-compose.sso-dev.yml` adds Keycloak (fictional users) behind Caddy on `auth.localhost`; the API trusts only Caddy's public root certificate. `make test-sso-dev` checks the setup.
- Request plumbing for the identity work (milestone M2): one error format (`application/problem+json` with stable codes), the injectable clock, the principal and organization scoping of every request, one transaction per request that the service commits before the response, `PHAROS_PUBLIC_URL`, `PHAROS_ORG_SLUG` and `PHAROS_SECRET_KEY` (with derived keys), an `organization` readiness check and a test that fails when a route is neither public nor covered by the role matrix.
- Sessions and CSRF protection (milestone M2): server-side sessions in Redis (`__Host-pharos_session` cookie, idle and absolute limits, per-user revocation, rotation), an Origin check and a per-session CSRF token on every state-changing request, and forwarded headers trusted from Caddy's pinned address only.
- Rate limiting and the audit log service (milestone M2): atomic per-address and per-account sign-in throttling with progressive delay and no lockout, and an append-only audit service with a fixed event catalogue, a separate transaction for failed attempts and keyed hashes instead of client addresses.
- Local accounts (milestone M2): password sign-in with Argon2id (`PHAROS_LOCAL_LOGIN`: `break-glass` by default, `on`, `off`), sign-out, `GET /api/me`, and operator commands `create-org`, `create-admin`, `set-password` and `unlock` (`python -m pharos.cli`). Failures all look alike, are throttled with growing waits and never lock an account out.
- Profile and onboarding API (milestone M2): profession, interests, language, AI level and department choices from fixed catalogues, completion with start and end timestamps, language precedence (own choice, browser, installation default) and the professions and departments lists.
- Single sign-on (milestone M2): authorization code flow with PKCE for any OpenID Connect provider, users found or created by issuer and subject (never by e-mail), department from a configurable claim, sign-out that also ends the provider session, and a Keycloak-based check of the whole flow (`make test-sso-dev`). New dependencies: `joserfc` and `httpx` (now a runtime dependency, used only by the identity-provider client).
- Onboarding (milestone M2): a four-step questionnaire in four languages (profession and optional department, interests, language, experience with AI) that saves each answer, can be completed with the keyboard alone in well under two minutes, continues where the person stopped and sends people who have not finished it there before anything else. The new texts in Azerbaijani, Turkish and Russian are unreviewed by native speakers (F-01).
- Sign-in pages and app shell (milestone M2): a login page in four languages with single sign-on and password forms (shown according to `GET /api/auth/config`), errors for wrong credentials, too many attempts and failed single sign-on, an account menu with sign-out, and a gate that sends signed-out visitors to sign in and back to the page they asked for. The new texts in Azerbaijani, Turkish and Russian are unreviewed by native speakers (F-01).
- Microsoft Entra ID preset (milestone M2): `PHAROS_OIDC_PRESET=entra` with `PHAROS_ENTRA_TENANT_ID` pins sign-in to one directory (the `common`, `organizations` and `consumers` aliases and domain names are refused), identifies people by object id, requires a version 2.0 token from that directory, refuses guests and personal accounts by default, and fills the department from Microsoft Graph without ever depending on it. Tested against Entra-shaped mocks only; real Entra ID is not tested.
- People management (milestone M2): `GET /api/users` and `PATCH /api/users/{id}/role|status` for administrators. Nobody changes their own account, two administrators cannot remove each other at the same moment (row locks plus a re-check of the caller), a change ends the person's sessions, and every change is audited.
- Single sign-on guides for Keycloak, Microsoft Entra ID and any other OpenID Connect provider (`docs/guides/`), `make dev-sso` for a development Keycloak, `make org` and `make admin` for the first steps after the stack is up, a section on private certificate authorities, and a test that fails when a setting of the API cannot be set through Compose or is missing from `deploy/.env.example`.
- Hardening after the whole-milestone security review: the worker and scheduler no longer receive the root key or the identity-provider secret, Redis has a memory limit, requests take a database connection only when they use it (a burst of sign-ins cannot use the pool up), single sign-on start is limited per IPv6 /64 and overall, password sessions of non-administrators end at once under `break-glass`, Entra guests are also recognized through Microsoft Graph, the route-coverage test now compares the matrix roles with the roles the route enforces, and the development Keycloak answers only private clients.
- Browser tests against the real stack (`make test-stack-e2e`): Caddy over HTTPS, the web app, the API, PostgreSQL, Redis and a development Keycloak.
