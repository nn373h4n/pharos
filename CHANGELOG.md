# Changelog

All notable changes are listed here, newest first. The format follows [Keep a Changelog](https://keepachangelog.com/) and the project uses [Semantic Versioning](https://semver.org/). Nothing has been released yet.

## [Unreleased]

### Fixed

- A feed in an encoding the XML parser does not know (for example EBCDIC) could hide its document type declaration from the check that refuses declarations and entities; such a feed is now refused (found by the whole-milestone review of M3).
- Caddy listens on the same port numbers the host publishes, and the HTTP-to-HTTPS redirect now names the configured domain and HTTPS port. The automatic redirect reflected the request's Host header, an open redirect; it is disabled and `make test-compose` checks it.

### Changed

- Redis now has two users instead of one shared password (follow-up F-14): `pharos_api` for the API and `pharos_worker` for the worker and the scheduler. The worker's user can use only the Celery queue and `pharos:worker:*`, so a compromised worker can no longer forge or read sessions. **Upgrading:** add `PHAROS_REDIS_WORKER_PASSWORD` (a new random value, different from `PHAROS_REDIS_PASSWORD`) to `deploy/.env` before `docker compose up`; `make env` generates it for new installs.

- The worker and the scheduler connect to PostgreSQL as their own role, `pharos_worker`, which has no privilege on people, credentials, profiles or the audit log, and the worker refuses to start with any other role. Tasks have time limits, worker processes are recycled, and the scheduler (`beat`) no longer has a route to the internet. **Upgrading:** add `PHAROS_WORKER_DB_PASSWORD` to `deploy/.env` and recreate the database volume (the role is only created on first start); see `docs/DEPLOYMENT.md`, "Upgrading to M3".

### Added

- The model gateway (milestone M4, `pharos.llm`): the one door to a language model, on the LiteLLM SDK (pinned). Only public article text can be sent, text is masked, the model has no tools, answers must fit a schema, spending is booked before each call against a small daily cap (80% warning, 100% stop, fail closed), and nothing about the content is logged. Off by default (`PHAROS_LLM_PROVIDER=off`); a fake provider serves tests and demos. Migration 0005 adds the content-free usage record `llm_usage`.
- Real-stack tests for ingestion (milestone M3, `make test-stack-e2e`): a fake feed host that only the worker can reach (a test-only Compose overlay), the whole path of an article, hostile and huge feeds, the places inside the stack that the worker must never reach, personal feeds and a disabled owner, and accessibility of the new pages.
- The feeds of a person whose account is disabled or deprovisioned are no longer fetched (follow-up F-32, migration 0004): the worker role may read the state of an account (`users.org_id`, `id`, `status`) and nothing else about people, takes only the personal feeds of active owners when it leases, and checks again before it fetches. ADR-0014 (proposed).
- Personal feeds (milestone M3, `pharos.feeds` and the page `/my-feeds`): every signed-in person can follow up to five RSS or Atom feeds of their own, fetched at most hourly, with their latest fetches and articles, seen by nobody else (not an administrator, not another organization). The address is checked like an organization source and a refused address is audited; `PHAROS_PERSONAL_FEEDS=off` removes the feature. No database migration.
- `python -m pharos.cli import-sources [--file PATH] [--dry-run]` (milestone M3): adds the starter catalogue of public sources to the organization, every source switched off, all or nothing, never changing a source that already exists. The catalogue file is checked with the rules of the Sources API; the list that ships has 25 public sources approved by the maintainer (16 feeds, 7 GitHub repositories, 2 Hacker News searches), each checked against Pharos's own feed rules before it was listed.
- Scheduled fetching (milestone M3, `pharos.ingest`): every minute the worker leases the sources that are due and fetches each one, at most 20 per minute, one request per host every five seconds, with no database transaction open while it waits for the network. Failures back off (doubling up to a day, `Retry-After` obeyed); a source that keeps failing is tried once a day. Old fetch history, raw items and items are removed on a schedule. Fetched entries are stored as raw items; turning them into items is the next step (M3-08).
- The RSS and Atom connector and the feed parser (milestone M3, `pharos.ingest`): a feed is refused if it has a document type declaration, an entity or an external reference, or is absurdly large or deep; titles and excerpts become short plain text without markup, look-alike or invisible characters; only absolute `http(s)` links are kept; fetches are conditional (`ETag`, `Last-Modified`) and go through `SafeHttpClient`. New dependencies: `feedparser`, `nh3`, `defusedxml`. Nothing schedules it yet (M3-07).
- Database tables for sources and ingestion (migration 0003, milestone M3): `sources`, `fetch_runs`, `raw_items`, `items`, `item_sources`. They belong to the organization under row-level security; a personal feed is visible to its owner only, administrators included; the worker role gets column-level access to these tables and nothing else. Run `docker compose ... run --rm migrate` after upgrading (the demo default applies it on start).
- `SafeHttpClient` (milestone M3): the only way connectors reach the internet. It checks every address a name resolves to at connect time and connects to the checked address (no DNS rebinding window), follows at most 3 redirects and re-checks each hop, allows only ports 80 and 443, refuses credentials in URLs and compressed answers, caps the body at 2 MiB and the whole request at a wall-clock deadline, ignores proxy environment variables, and returns only coarse error kinds. A bearer token is sent only over HTTPS to its own host. Import-linter now limits `httpx` and `httpcore` to this client and the identity-provider client, and keeps API modules from importing the fetcher.
- Platform skeleton (milestone M1):
  - Backend: FastAPI application with request ids, JSON logs that mask secrets, `/api/healthz` and `/api/readyz`, and an Alembic baseline that creates `organizations` under PostgreSQL row-level security.
  - Worker: Celery worker and scheduler with a heartbeat that `/api/readyz` checks.
  - Web app: Next.js pages in English, Azerbaijani, Turkish and Russian, light and dark themes, WCAG 2.2 AA checks in the test suite.
  - Deployment: Docker Compose stack with Caddy, isolated networks, hardened containers, PostgreSQL with pgvector and Redis (`make env`, `make dev`).
  - Delivery: pull-request checks, security scans (gitleaks, CodeQL, Trivy), weekly Dependabot updates, a protected `main` branch.
- Development identity provider: `deploy/docker-compose.sso-dev.yml` adds Keycloak (fictional users) behind Caddy on `auth.localhost`; the API trusts only Caddy's public root certificate. `make test-sso-dev` checks the setup.
- Request plumbing for the identity work (milestone M2): one error format (`application/problem+json` with stable codes), the injectable clock, the principal and organization scoping of every request, one transaction per request that the service commits before the response, `PHAROS_PUBLIC_URL`, `PHAROS_ORG_SLUG` and `PHAROS_SECRET_KEY` (with derived keys), an `organization` readiness check and a test that fails when a route is neither public nor covered by the role matrix.
- Sessions and CSRF protection (milestone M2): server-side sessions in Redis (`__Host-pharos_session` cookie, idle and absolute limits, per-user revocation, rotation), an Origin check and a per-session CSRF token on every state-changing request, and forwarded headers trusted from Caddy's pinned address only.
- Rate limiting and the audit log service (milestone M2): atomic per-address and per-account sign-in throttling with progressive delay and no lockout, and an append-only audit service with a fixed event catalogue, a separate transaction for failed attempts and keyed hashes instead of client addresses.
- Local accounts (milestone M2): password sign-in with Argon2id (`PHAROS_LOCAL_LOGIN`: `break-glass` by default, `on`, `off`), sign-out, `GET /api/me`, and operator commands `create-org`, `create-admin`, `set-password` and `unlock` (`python -m pharos.cli`). Failures all look alike, are throttled with growing waits and never lock an account out.
- Profile and onboarding API (milestone M2): profession, interests, language, AI level and department choices from fixed catalogues, completion with start and end timestamps, language precedence (own choice, browser, installation default) and the professions and departments lists.
- Single sign-on (milestone M2): authorization code flow with PKCE for any OpenID Connect provider, users found or created by issuer and subject (never by e-mail), department from a configurable claim, sign-out that also ends the provider session, and a Keycloak-based check of the whole flow (`make test-sso-dev`). New dependencies: `joserfc` and `httpx` (now a runtime dependency, used only by the identity-provider client).
- Onboarding (milestone M2): a four-step questionnaire in four languages (profession and optional department, interests, language, experience with AI) that saves each answer, can be completed with the keyboard alone in well under two minutes, continues where the person stopped and sends people who have not finished it there before anything else. The new texts in Azerbaijani, Turkish and Russian are unreviewed by native speakers (F-01).
- Sign-in pages and app shell (milestone M2): a login page in four languages with single sign-on and password forms (shown according to `GET /api/auth/config`), errors for wrong credentials, too many attempts and failed single sign-on, an account menu with sign-out, and a gate that sends signed-out visitors to sign in and back to the page they asked for. The new texts in Azerbaijani, Turkish and Russian are unreviewed by native speakers (F-01).
- Microsoft Entra ID preset (milestone M2): `PHAROS_OIDC_PRESET=entra` with `PHAROS_ENTRA_TENANT_ID` pins sign-in to one directory (the `common`, `organizations` and `consumers` aliases and domain names are refused), identifies people by object id, requires a version 2.0 token from that directory, refuses guests and personal accounts by default, and fills the department from Microsoft Graph without ever depending on it. Tested against Entra-shaped mocks only; real Entra ID is not tested.
- People management (milestone M2): `GET /api/users` and `PATCH /api/users/{id}/role|status` for administrators. Nobody changes their own account, two administrators cannot remove each other at the same moment (row locks plus a re-check of the caller), a change ends the person's sessions, and every change is audited.
- Single sign-on guides for Keycloak, Microsoft Entra ID and any other OpenID Connect provider (`docs/guides/`), `make dev-sso` for a development Keycloak, `make org` and `make admin` for the first steps after the stack is up, a section on private certificate authorities, and a test that fails when a setting of the API cannot be set through Compose or is missing from `deploy/.env.example`.
- Hardening after the whole-milestone security review: the worker and scheduler no longer receive the root key or the identity-provider secret, Redis has a memory limit, requests take a database connection only when they use it (a burst of sign-ins cannot use the pool up), single sign-on start is limited per IPv6 /64 and overall, password sessions of non-administrators end at once under `break-glass`, Entra guests are also recognized through Microsoft Graph, the route-coverage test now compares the matrix roles with the roles the route enforces, and the development Keycloak answers only private clients.
- Browser tests against the real stack (`make test-stack-e2e`): Caddy over HTTPS, the web app, the API, PostgreSQL, Redis and a development Keycloak. They cover the onboarding by keyboard in under two minutes, WCAG 2.2 AA checks of the signed-in start page and the first question in four languages, two themes and two screen sizes, and sign-in at the provider, the session cookie, sign-out ending the provider session, break-glass password sign-in, refusals, a disabled account, and the audit log. CI runs them and the Keycloak stack check as two new jobs.
- Project files: Apache-2.0 license, contribution guide with DCO sign-off, code of conduct, security policy, governance, issue and pull request templates.
- Architecture decision records 0001-0010, architecture, data model, threat model, API and deployment documents.
