# Threat model

Status: v0 (milestone M1). Every control below must gain an automated test before the milestone that ships it is accepted. Nothing here is claimed as proven until its test exists.

## Assets

- Credentials: LLM API keys, OIDC client secret, session cookies, the encryption master key.
- Organization data: user profiles, interaction history, audit log, and (phase 2) internal ideas and stories.
- Integrity of what employees read: summaries and "how to apply" text generated from external content.
- The organization's LLM budget and the availability of the service.

## Trust boundaries

1. Browser ↔ Caddy/web/api (untrusted client).
2. api/worker ↔ external networks: OIDC provider, content sources, LLM providers (untrusted responses).
3. External content and LLM output ↔ the rest of the system (always untrusted data).
4. Application role ↔ database (RLS applies; the role is not the table owner).
5. Employee ↔ third-party AI tool, when the user pastes a "Try this" prompt.

## Threats and controls

| Threat | Control | Test |
| --- | --- | --- |
| Identity spoofing | OIDC Authorization Code + PKCE, `state`/`nonce`, issuer and audience checks; backend BFF, no tokens in the browser; httpOnly, Secure, SameSite=Lax session cookie in Redis | Forged nonce, expired token, wrong audience |
| Tenant escape | `org_id` only from the session; mandatory filter in the repository layer; PostgreSQL RLS as the second line; tenant-aware cache keys | Two-organization fixture, cross-tenant test for every endpoint |
| Missing authorization (RBAC) | `admin` / `editor` / `member` checked in the service layer, not only in the UI | Role × endpoint matrix; the role is read from the database on every request, administrators changing people lock the administrator rows and are re-checked, and nobody changes their own account (M2-07) |
| Prompt injection, content poisoning | Product LLM has no tools; external text wrapped in delimiters and declared as data; JSON schema validation; link filter; `try_prompt` validation; low-quality or suspicious items go to an editor queue | Injection corpus regression test |
| Data leak through "Try this" (R1, P0) | Each card opens only the AI tools the admin has approved, shows a "do not paste sensitive data" notice, and uses placeholders instead of real data; click counts are aggregate only | UX review, user training material |
| SSRF | `SafeHttpClient` (`backend/src/pharos/net`): http/https on ports 80 and 443 only, no credentials in URLs, allow-list of global unicast addresses plus an explicit deny list (NAT64, 6to4, Teredo, mapped IPv6, 192.0.0.0/24), every resolved address checked at connect time and the checked address used (no rebinding window), at most 3 redirects each re-checked, own public host refused, bearer token only to its own host over HTTPS, 2 MiB cap and total deadline, no compression, no proxy variables, coarse errors; default-deny network egress. The test-only address allowance is refused by `Settings` outside `environment=test` and is never passed by Compose | 169.254.169.254, DNS rebinding, redirect chain, `127.1` and decimal forms |
| Hostile feed document (XML bombs, XXE, huge or deep documents, hostile text and links) | `pharos.ingest`: the document is read once with `defusedxml` and refused if it has a document type declaration, an entity or an external reference, more than 100,000 elements or more than 64 levels (a document that is not well-formed is parsed tolerantly only if a scan of the bytes, in the encodings an attacker could choose, finds no declaration); `feedparser` gets bytes only and at most 200 entries are read; titles (300) and excerpts (500) are reduced to plain text with `nh3`, NFKC, and no control, bidirectional or zero-width characters; only absolute `http(s)` links without credentials, white space or markup survive (matching the database constraint); the article page is never fetched; failures are fixed words (no URL, no address, no feed text) | `backend/tests/ingest` (hostile feed corpus with a mutation check for every control) |
| XSS | LLM output is plain text or restricted markdown; server-side sanitization with `nh3`; strict CSP; React escaping | Malicious HTML/markdown corpus |
| CSRF | Same origin behind Caddy, SameSite=Lax cookie, CSRF token on mutating requests | Cross-origin POST |
| Secret exposure | AES-256-GCM envelope encryption, `key_version` rotation; masking filter on logs; gitleaks pre-commit and CI; fake data only in the repository | Search logs for key patterns |
| Data leaving through a compromised container (SSRF, exfiltration) | `postgres`, `redis` and `web` have no route to the internet (Docker `internal: true` networks); `caddy` and `web` are not on the `data` network, so they cannot reach the database or Redis; only `api` and `worker` join `egress` (the scheduler `beat` only needs Redis); no database or Redis port is published; the database superuser cannot log in over the network; all containers drop every capability, forbid privilege escalation and have a read-only root file system | `make test-compose` (isolation checks, each with a positive control; database login checks; hardening checks) |
| Code execution through the task queue | Celery accepts JSON only (no pickle); Redis is reachable from the internal network only and requires a password in production; a task payload is data, never code | `tests/workers/test_app.py` (serializer and `accept_content`) |
| DoS and cost abuse | Per-user and per-organization rate limits (Redis); LLM budget with 80% warning and 100% stop; queue backpressure | Limit-exceeded tests |
| Supply chain | In place: lockfiles installed with `--frozen`, Dependabot, CodeQL, gitleaks and Trivy as required CI checks, GitHub Actions pinned to commit SHAs, CI tools run as digest-pinned images, DCO sign-off, protected `main`. Planned (TASKS F-05, F-07): digest-pinned base images, SBOM and signed images by M5 | Required CI checks |
| Misuse of the development agent | PreToolUse guard hook, deny rules, gitleaks pre-commit; planned devcontainer | `tests/hooks/test_guard.sh` |

## Audit

Audited events: sign-in and sign-out, role changes, LLM settings and keys, source added or removed, exports, budget changes. Audit records never contain secrets or content.

How it is built (M2): events come from a fixed catalogue (`AuditAction` in `backend/src/pharos/core/audit.py`; a new event is added there in the pull request that raises it). The application role can only INSERT and SELECT audit rows. A successful action writes its row in the same transaction as the change; a failed attempt writes its row in a transaction of its own so it survives the rollback (best effort: a failing audit write is logged and does not turn into an outage). The client address is stored only as an HMAC with a key derived from `PHAROS_SECRET_KEY`. Detail fields are short scalars, and a key that looks like a secret (`password`, `token`, `cookie`, ...) is refused as a programming error.

Sign-in throttling (`backend/src/pharos/core/ratelimit.py`): counters live only in Redis, keyed by hashes of the account and address. Per address: 30 attempts a minute. Per account and address: three free failures, then waits of 2, 4, 8 ... seconds up to 5 minutes. Per account across addresses: ten free failures, then waits up to 1 minute. There is no hard lockout, so knowing someone's account name does not let an attacker lock them out; an operator can clear the counters. Unknown accounts are throttled exactly like known ones.

## Company-internal content (phase 2)

Not sent to a cloud LLM by default. If an admin enables it, personal and sensitive data is masked first (email, phone, IBAN, national ID, personal names) and the setting change is audited. Privacy claims such as "anonymous" or "never leaves the network" are written only when the architecture and tests prove them.

## Residual risks and open items

- R1 depends on user behaviour; the controls reduce but do not remove it.
- Row-level security does not defend against code that executes arbitrary SQL as the application role, because that role can change `app.org_id` itself. Mitigations: parameterized queries only, LLM output and external text never reach SQL, the pool resets `app.org_id` on check-in, and `/readyz` verifies the role has no `BYPASSRLS`, is not a superuser and owns no table. See [DATA_MODEL.md](DATA_MODEL.md#row-level-security).
- The web app sends `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy` and `Permissions-Policy`, but not yet a strict Content-Security-Policy. The CSP is planned with the output sanitization work (ADR-0009); until then, XSS protection relies on React escaping and on rendering no untrusted content.
- Docker Compose cannot restrict *which* internet hosts the `egress` services reach. Until the operator adds a host firewall rule or an outbound proxy, a compromised `api`, `worker` or `beat` can reach any host. This is the main gap between the "default-deny egress" principle and what ships. See [DEPLOYMENT.md](DEPLOYMENT.md).
- Containers on an `internal: true` network can still reach services that listen on the host's bridge gateway address, because that traffic does not pass through the forwarding rules. A host firewall rule for the Docker subnets closes this (see [DEPLOYMENT.md](DEPLOYMENT.md)); it was reasoned about from Docker's documentation, not tested.
- `caddy` runs as root inside its container (all capabilities dropped except `NET_BIND_SERVICE`). Database and Redis passwords are environment variables readable by anyone who can run `docker inspect`.
- Session records in Redis are not signed. Since M3-02 the worker and the scheduler connect as their own Redis user (`pharos_worker`), which can use only the Celery queue (`celery*`, kombu's `_kombu.*`, `unacked*`, the pidbox keys) and `pharos:worker:*`; it cannot read, write or list session records, rate-limit counters or sign-in state, and neither Redis user can run the dangerous commands (`CONFIG`, `ACL`, `KEYS`, `FLUSHALL`, ...). The default user is off. The rules live in `deploy/redis/start.sh`, and the integration tests start Redis with that same script. Follow-up F-14 is closed. The worker's user also cannot list key names, count keys, switch database or load functions; its key patterns are exact so that a key like `pharos:rl:<x>.celery.pidbox` stays closed. What remains: a compromised worker can still fill the 200 MB Redis through its own keys (`noeviction` then makes every write fail, so sign-in stops; the rate limiter fails closed, so this denies service and does not open the door to guessing) or keep Redis busy with a looping script (kombu needs scripts); a separate Redis instance for sessions would remove this and is not planned. The API user can still touch everything in Redis (it is the trusted process), and a worker that can reach the queue can still enqueue tasks, which is why tasks carry IDs only (ADR-0012).
- Single sign-on trusts the configured provider completely for who a person is: whoever controls an account at the provider can sign in as its subject. The controls are around the protocol, not the provider: state and nonce, PKCE, a one-time binding cookie, exact issuer and audience, a fixed signature algorithm list, identity by subject only (never e-mail; with Entra the object id inside one pinned directory, so a guest or another directory cannot collide), no role from the provider, and a disabled account that stays disabled. The provider's own multi-factor authentication is the provider's job. The API reaches the provider with a dedicated client (the one exception to `SafeHttpClient`) that follows no redirects, limits sizes and calls only endpoints from the validated discovery document (plus, with the Entra preset, one fixed Microsoft Graph address with a short timeout); a malicious discovery document can still point the API at an internal address, which is why the issuer is configuration, never user input. Tested against a fake provider (negative suite) and a real Keycloak; Entra ID only with recorded shapes (M2-06).
- The single sign-on start and callback are limited to 120 requests a minute per source address, and refusals that anyone can cause without having started a flow (no state, unknown state, throttled) are logged but not written to the audit log one by one. People behind one shared egress address share that allowance; it is meant to stop a loop, not a crowd. A flood from many addresses is a job for the edge (firewall or proxy), not for this counter.
- Local sign-in commits the database (last login, audit row) before it creates the Redis session, as ADR-0011 says. If Redis fails in between, the audit log records a successful sign-in for which no session exists; the user sees a 503 and tries again. A local session also stays valid after `PHAROS_LOCAL_LOGIN` is switched off until it expires (follow-up F-15), and a stored hash made with older parameters verifies in slightly different time than the dummy hash used for unknown users (F-16).
- The worker and the scheduler are started without the root key, the identity-provider secret and the sign-in mode (`PHAROS_PROCESS=worker`; Settings refuses to start a worker that is given them), so a compromised worker cannot read them from its environment. It holds its own, limited Redis credentials (F-14, closed) and its own database role (`pharos_worker`, M3-03), which has no privilege on people, credentials, profiles or the audit log; the worker refuses to start with any other role.
- Items made from a feed (M3-08): a link is reduced to a canonical form without decoding its query, so a crafted link can neither lengthen past the database limit and block a whole feed nor collide with another article; only the source that first reported an article may change its text, and text that a hold rule flags never replaces the text of an existing item (the worker cannot change `status`). Hold rules are flags for a person, not a defence: text from a feed reaches the model as delimited data in every case (M4). Residual risk: F-24.
- GitHub and Hacker News sources (M3-09): the GitHub token (optional, no scopes) reaches only the worker, is sent as a `Bearer` that `SafeHttpClient` binds to `api.github.com` over HTTPS (dropped on any redirect to another host), and appears in no URL, error, log line, `repr` or stored configuration; a production API process refuses to start with it and Settings never echo a refused value. The repository and the search words are validated and checked again at every fetch, so a tampered stored configuration cannot change host, path or parameters. JSON answers are read strictly (UTF-8, depth and number limits, wrong types skipped), cleaned like feed entries, and a spent rate limit (`X-RateLimit-*`, `Retry-After`) delays the next run instead of being retried. Residual risk: a rate-limit answer can delay a source for at most 24 hours, like any `Retry-After`.
- The sources API (M3-10a): only administrators change sources and editors read them; every statement filters by organization and by `owner_user_id IS NULL`, so a person's own feeds are out of reach of administrators; the application role may change only the configuration columns, never the lease, validators or failure state. The API can validate a configuration but cannot load anything that fetches: `pharos.sources` imports the network-free `pharos.ingest.sourceconfig`, and a strict import-linter contract (indirect imports included) fails if it, or anything it imports, reaches the HTTP client, the fetcher, the connectors or the workers. An address that can only be internal is refused when typed and audited (in any spelling a client accepts: decimal, hex or short IPv4, other dot characters such as U+3002, and names without a dot), and again when a source is switched on, a duplicate or an over-the-cap request leaves a failure row, and audit entries never hold the configuration. Residual risk: the early refusal is a convenience, not the defence (a public name that resolves to an internal address is stopped by `SafeHttpClient` at connect time); after a source's address changes, the stored validators of the old address are sent once (harmless, the server answers 200); the import contracts see only static imports (a dynamic import, or an object reached through `app.state`, is invisible to them), and grimp treats `urllib` as one module, so the exception that lets `sourceconfig` use `urllib.parse` would also let a direct `urllib.request` import in that one file pass; a second contract forbids direct network imports in `pharos.sources`, and a test imports the API modules in a fresh interpreter to prove no HTTP library gets loaded. The cap of 200 sources is exact (creations take an advisory lock per organization).
- The items API (M3-10b): everybody signed in reads, only administrators and editors review. Held and hidden articles, the reason an article is held and the sources behind it are hidden from members (a held or hidden article answers like one that does not exist); every statement filters by organization and by `owner_user_id IS NULL`, the application role may change `status` and `hold_reason` and nothing else, and the pages are plain text with `http(s)` links (the rendering rules of ADR-0009 still apply in the browser). A decision is audited with the state it came from and is not undone by the worker. The two import contracts of the sources API apply to the items API too. Residual risk: a hold is a prompt for a person to look, not a safety control, because only the pipeline sets it and only when an article is created (TASKS F-24); an editor with a compromised session can hide or hold every article (audited, reversible). A decision is tied to the article's link, not to its text: the first source can still refresh the text of an approved, held or hidden article with text no rule flags, so a review that was based on text A can end up covering text B (TASKS F-26 proposes a precondition on the time the reviewer saw). Hiding clears a rule's flag and restoring shows the article, so a restore is an explicit approval whose trail is the audit log; the hide of an article under one address does not hide the same article published under another.
- The trial fetch (M3-10c, ADR-0013): the API asks the worker by name and sends two identifiers, never an address, so whoever can write to the broker cannot choose a URL; the message goes through the anonymous exchange to the one list the worker listens to, so the table of bindings that the worker's Redis user may write is never read (a review suspected that a planted binding could steer the API's all-keys Redis user into its own keys; it could not be reproduced with this Celery and kombu, and a test pins the property). The worker re-reads the source as its limited database role, only for an organization source, passes the host politeness gate, fetches once, writes nothing to the database and leaves a small answer under `pharos:worker:testfetch:*` with a two-minute expiry. The API treats that answer as untrusted data: a size limit before parsing, a strict schema (exact types, no unknown field, a fixed list of outcomes, a short lowercase word for the error code, at most five samples), the identifiers must equal the marker's, titles must already be plain text and links are checked again; anything else is shown as `unavailable`. The markers, cooldowns and counters live under `pharos:api:testfetch*`, which the worker's Redis user cannot read or write (tested), so a compromised worker cannot forge a marker, lift the cooldown or read another test. A test fetch is audited, limited to one per source every 30 seconds and ten a minute per organization, and refused if the stored address is internal now. Residual risk: a compromised worker can put any bounded, schema-valid text in front of an administrator for a test one of the administrators started, so titles must be shown as text (ADR-0009); the cooldown is per source and shared by all administrators; a trial ignores the source's own backoff, so a host that asked us to wait can be asked again by a person; the answer is polled, and a worker that never answers leaves it `pending` until the test id expires; a compromised worker can still fill the shared Redis through its own prefix (older than this change).
- The articles screen (M3-11a): titles, excerpts and source names come from third parties and are rendered as text by React, never as markup (no `dangerouslySetInnerHTML` anywhere); a link is made only if the address passes `safeHref` (absolute `http(s)`, a host directly after the slashes, no credentials, no white space, quotes, angle brackets or backslashes, at most 2048 characters), opens in a new tab with `rel="noopener noreferrer nofollow"` and shows its host, otherwise the title is plain text with a note. Every answer is checked for its shape before it is used. Hiding review buttons from members is a convenience: the backend refuses them with 403. Residual risk: there is still no Content-Security-Policy (F-03), so these rules are the only barrier against script in a title; a link to an arbitrary host is one click away for a person who chooses to follow it.
- The starter catalogue (M3-12): the file ships with the code and is read by an operator command, never by a request. Every entry passes the rules of the Sources API (type, interval, `sourceconfig`, which refuses addresses inside the network), feeds must use `https`, unknown fields are refused so an entry cannot ask to be switched on, and the file is limited to 100 entries and 512 KiB. Sources are always written switched off, credited to nobody, and audited as `source.created` by `operator_cli` with the origin `starter_catalogue`; the import runs as the application role inside the organization's transaction, under the same cap on sources as the API. Residual risk: `--file` takes any path the operator can read; its content is only parsed as data, and a wrong address is refused or fails safely at fetch time through `SafeHttpClient`.
- The sources screen (M3-11b): names, addresses, search words and the sample of a trial fetch are text from administrators or from third parties and are rendered as text only. The outcome and the problem code of a fetch are shown through fixed lists of words, never as received. Sample addresses pass the same `safeHref` and open with `rel="noopener noreferrer nofollow"`; the address of a feed on a card is not a link. Every change (add, edit, switch, delete, start of a trial) sends the CSRF token; identifiers go into a path only after a strict UUID check; the page asks for a trial's answer every two seconds for at most two minutes (one request at a time, stopped when the card goes away). Showing the controls only to administrators is a convenience: the backend decides (403). One step at a time is enforced in the page (`busy`), so a late answer cannot change what a button applies to. Residual risk: a trial that is running when the list reloads is no longer shown (the worker still finishes it and it counts against the cooldown) - F-29.
- Redis has a memory limit (`--maxmemory 200mb`, below the container's 256 MB) with `noeviction`: when it is full it refuses writes and sign-in fails closed, instead of the kernel killing it together with every session. Unfinished single sign-in records (10 minutes each) are bounded per address (an IPv6 /64 counts as one) and for the whole installation (600 a minute).
- The password path takes no database connection while it waits for the hashing queue, and a request takes none until it uses the database, so a burst of sign-ins cannot use the connection pool up. The single sign-on callback calls the provider before it touches the database for the same reason.
- The API trusts `X-Forwarded-For` from Caddy's pinned address (`PHAROS_CADDY_IP`). Another container could only use that address by taking it over, which Docker prevents inside a network while Caddy runs; `NET_ADMIN` and `NET_RAW` are dropped everywhere, so address spoofing from the web container is not possible. Not tested beyond the forged-header checks in `make test-compose`.
- Application logs pass through a regex masker. It covers common key names, headers, URLs and token formats, not every possible secret, so secrets must still not be logged on purpose.
- Azerbaijani output quality and local-model quality are unmeasured.
- The development agent guard is a guard rail, not a sandbox; its known limits are listed in `.claude/hooks/pre_bash_guard.py`.
- Backup, restore and retention defaults are undefined.
- External source terms of service must be checked per connector before it is enabled.
