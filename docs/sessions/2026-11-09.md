# Session 2026-11-09

## Goal

Decide F-47 (P2: monthly interaction counts next to the daily summary could reveal a smaller group by subtraction) on branch `test/f47-monthly-counts-stay-unpublished`. The maintainer chose path A: no code or data change; pin the rule with tests and write it down. Then an independent security review of that change. Nothing committed.

## Done, with evidence

- Read-only investigation: the table `interaction_counts_monthly` is read by nothing except the operator command `fold-interactions` and by tests. `pharos_app` and `pharos_worker` have no grant on it. The admin-only `GET /api/interactions/summary` (30 days, `SUMMARY_DAYS`) never reads it. Folded months end at least 90 days before today (minimum retention is 3 months), so no day and its month are published together today. The risk is latent, not live. Every day of a folded month was on the admin summary while it was recent, so a noted daily count could be subtracted from a monthly row shown later.
- New tests, no production code changed:
  - `backend/tests/test_interaction_windows.py`: every day 2024-2029 is in the sample; for each month count from `MIN_INTERACTIONS_RETENTION_MONTHS` to 120 the newest folded day is more than `SUMMARY_DAYS` back; an assert that the floor is 3; the smallest gap for 3 months equals 90 days.
  - `backend/tests/test_monthly_counts_unpublished.py`: a contract scan of the whole repo except `docs/`, `backend/tests/` and root Markdown files. Only `retention.py` and migration 0011 may name the table. A positive control proves the scan visits alembic, `backend/src`, `frontend/src`, `scripts` and `deploy`, and finds the table where it is written.
  - `test_no_function_or_view_reads_the_monthly_counts` in `backend/tests/integration/test_retention.py`: checks all non-system schemas in `pg_proc`, `pg_views`, `pg_matviews`, and policies and rules, with ILIKE and a positive control. It also fails on any grantee of the table other than the owner (including PUBLIC or a new reporting role).
- Independent review by `security-reviewer`:
  - No P0.
  - P1: the first wording, "the two never overlap", was true only at one moment (see above). The rule was rewritten, approved by the maintainer on 2026-11-09.
  - P2: the window test had a hard-coded `range(3, 25)`; it now runs from `MIN_INTERACTIONS_RETENTION_MONTHS` to 120 with the floor assert. The file scan had blind spots; it now covers the whole repo outside the exclusions above, with the positive control.
  - P3: the database test now covers all non-system schemas, ILIKE, policies and rules, and fails on any grantee other than the owner. `fold-interactions` prints and audits one total of folded rows that includes groups dropped for having fewer than five people (low risk, written in `THREAT_MODEL.md`).
  - All findings are fixed or documented. The fixes were NOT reviewed a second time.
- Rule (current wording, in ADR-0025, `docs/DEPLOYMENT.md` and `docs/THREAT_MODEL.md`): the monthly counts must not be shown to anyone who could see the daily summary while those months were recent (administrators), nor together with overlapping periods (a day and its month, a month and a quarter). Publishing the monthly counts or a summary window of 90+ days needs a new decision first. The tests are only a guard against a future change; they are not proof over time.
- Mutation checks, each broken on purpose, caught, then restored:
  - Earlier round: `SUMMARY_DAYS = 91`; a new file naming the table; a view, a materialized view and a function added in migration 0011. Migration 0011 is unchanged in git.
  - Review round: minimum retention 1 (window tests fail, plus the `test_deploy_wiring` retention-defaults test; the wider run was stopped at the first failure, so other tests that react are unknown); table name in a new alembic file and in the Makefile (scan fails); `GRANT SELECT` to a new role and to PUBLIC (grants assert fails); a view and a policy mentioning the table in capitals (mention assert fails).
- Bookkeeping: `TASKS.md` (F-47 row), `CHANGELOG.md` (Unreleased > Added, one line), this note.

## Open issues

- The pilot's SQL report is outside the repo. Its rule is the operator's, and nothing checks it.
- The "two months" case (two folded months subtracted from each other) is reasoned, not tested. Months do not overlap, so no subtraction is expected.
- The window margin is thin: 90 days equals the SQL function's clamp. Only the tests pin it.
- Nothing stops an administrator who noted the daily counts from subtracting, if the monthly rows are ever shown to them. The rule is the only guard.
- The fixes from the review were not reviewed a second time.
- The wider mutation run was stopped at the first failure; which other tests react to the minimum-retention mutation is unknown.
